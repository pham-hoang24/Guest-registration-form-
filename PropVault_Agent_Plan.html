PropVault — Owner Dashboard

Implementation Plan  ·  Agent Build Specifications

Version 1.0  ·  Server-side PDF  ·  JWT Auth  ·  No PII in frontend

 

Architecture Decision Record

Three decisions are locked before any agent begins work:

 

•       PDF generation is server-side only. The frontend never receives raw tenant PII for PDF rendering. The Print / Download Form button calls GET /v1/owner/submissions/:id/pdf and downloads the blob. No pdf-lib dependency in the frontend. No fillModalFormPdf.ts utility.

•       Authentication uses JWT Bearer tokens. The login flow already exists. Token is obtained from the existing login endpoint and sent as Authorization: Bearer <token> on every owner API request. Middleware validates the token, resolves owner identity, and checks property/submission ownership before any data is returned.

•       GET /v1/owner/properties is in scope for this iteration. The property strip in the dashboard UI is data-driven, not hardcoded. The backend exposes a list of properties the authenticated owner controls.

AGENT 1

Auth Middleware

Backend · JWT validation · Owner identity · Request guard

 

 

Goal

Every owner endpoint is protected. Unauthenticated requests return 401. Requests from owners who do not own the requested resource return 403. No owner endpoint can be written, tested, or merged without this middleware in place.

 

 

Context — What already exists

•       A login flow exists that issues a JWT. Confirm the signing secret/key location (environment variable, secrets manager) before proceeding.

•       The token payload includes at minimum: sub (owner user ID), iat, exp.

•       If the token includes additional claims (e.g. role, propertyIds) document them here before writing middleware.

 

 

Deliverables

1.     middleware/authenticateOwner.ts — Express/Fastify middleware that:

◦       Reads Authorization header; rejects with 401 if missing or malformed.

◦       Verifies JWT signature and expiry; rejects with 401 if invalid.

◦       Attaches req.owner = { id, email } to the request object.

◦       Never logs or exposes the token itself.

 

2.     middleware/authorizeProperty.ts — ownership check middleware:

◦       Reads propertyId from req.params.propertyId.

◦       Queries DB: SELECT owner_id FROM properties WHERE id = propertyId.

◦       Returns 403 if req.owner.id !== owner_id.

◦       Returns 404 if property does not exist.

 

3.     middleware/authorizeSubmission.ts — submission ownership check:

◦       Reads submissionId from req.params.id.

◦       Queries DB: SELECT p.owner_id FROM submissions s JOIN properties p ON s.property_id = p.id WHERE s.id = submissionId.

◦       Returns 403 if req.owner.id !== owner_id. Returns 404 if not found.

 

4.     types/express.d.ts — TypeScript augmentation:

◦       Declare Request.owner: { id: string; email: string } so all downstream handlers have typed access.

 

 

Token flow diagram

Client                  Middleware              Handler

  |                         |                      |

  |-- GET /v1/owner/... --> |                      |

  |   Authorization:        |                      |

  |   Bearer <jwt>          |                      |

  |                    verify(jwt, secret)         |

  |                    attach req.owner            |

  |                    check ownership             |

  |                         |--- req.owner.id ---> |

  |                         |   (safe to use)      |

 

 

Acceptance criteria

•       GET /v1/owner/properties with no token → 401 { error: 'Unauthorized' }

•       GET /v1/owner/properties with expired token → 401 { error: 'Token expired' }

•       GET /v1/owner/properties/:id/submissions where owner does not own property → 403

•       GET /v1/owner/submissions/:id where owner does not own submission → 403

•       All checks pass for a valid token and correct ownership.

AGENT 2

Backend Endpoints + Server-Side PDF

Backend · 4 REST routes · DB queries · PDF generation

 

 

Prerequisite

Agent 1 middleware must be merged and tested before any route in this agent is written. All routes below are wrapped with authenticateOwner + the appropriate ownership check middleware.

 

 

Route 1 — GET /v1/owner/properties

Returns the list of properties owned by the authenticated owner. Used to populate the property strip tabs in the dashboard.

 

DB query

SELECT id, name, address, status

FROM properties

WHERE owner_id = req.owner.id

ORDER BY name ASC

 

Response — 200

[

  { "id": "prop_abc", "name": "Maple Heights 3B",

    "address": "14 Maple Street, Helsinki 00100",

    "status": "occupied" }

]

Status values: "occupied" | "vacant" | "pending"

 

 

Route 2 — GET /v1/owner/properties/:propertyId/submissions

Returns the submission list for one property. Middleware: authenticateOwner + authorizeProperty.

 

DB query

SELECT s.id, s.created_at, s.status,

       (s.payload->>'fullName') AS tenant_name

FROM submissions s

WHERE s.property_id = :propertyId

ORDER BY s.created_at DESC

 

Response — 200

[{ "id": "sub_xyz", "createdAt": "2024-03-01T10:00:00Z",

   "status": "submitted", "tenantName": "Ana Maria Torres" }]

 

 

Route 3 — GET /v1/owner/submissions/:id

Returns full submission detail including decrypted guest payload. Middleware: authenticateOwner + authorizeSubmission. The payload is decrypted at this layer if stored encrypted at rest.

 

DB query

SELECT s.id, s.property_id, s.created_at, s.status,

       decrypt(s.payload) AS payload

FROM submissions s

WHERE s.id = :submissionId

 

Response — 200

{ "id": "sub_xyz",

  "propertyId": "prop_abc",

  "createdAt": "2024-03-01T10:00:00Z",

  "status": "submitted",

  "payload": {

    "fullName": "Ana Maria Torres",

    "nationality": "ES",

    "documentNumber": "XAB123456",

    "address": "Calle de Alcalá 42, 28014 Madrid",

    "dateOfBirth": "1990-06-14",

    "checkInDate": "2024-03-01",

    "checkOutDate": "2026-12-31",

    "phone": "+34600000000",

    "email": "ana@example.com"

  }

}

 

 

Route 4 — GET /v1/owner/submissions/:id/pdf

Generates and returns the filled official Matkustajailmoitus PDF. No PII is sent to the frontend for PDF generation. Middleware: authenticateOwner + authorizeSubmission.

 

Implementation

•       Load the PDF template from the server filesystem (e.g. assets/matkustajailmoitus-template.pdf). Do not fetch it at runtime from an external URL.

•       Fetch the submission payload from the DB (same query as Route 3).

•       Fill fields using pdf-lib (Node.js). See the PDF Field Mapping Reference in the Overview section for the complete field list.

•       Call form.flatten() before returning so the PDF cannot be edited after download.

•       Return the filled PDF bytes with headers:

 

Content-Type: application/pdf

Content-Disposition: attachment; filename="Matkustajailmoitus_Torres_AnaMaria.pdf"

 

Filename rule

Derive filename from payload.fullName: last word = surname, remaining = given names. Sanitize: remove non-ASCII, replace spaces with underscores. Format: Matkustajailmoitus_Surname_GivenNames.pdf

 

Server-side PDF fill — code outline

import { PDFDocument } from 'pdf-lib';

import fs from 'fs';

 

const tplBytes = fs.readFileSync('assets/matkustajailmoitus-template.pdf');

const pdfDoc   = await PDFDocument.load(tplBytes);

const form     = pdfDoc.getForm();

 

// Map payload to fields (see Overview mapping table)

form.getTextField('Text1').setText(sukunimi);

form.getTextField('Text2').setText(etunimet);

// ... remaining fields ...

form.getCheckBox('Check Box5').check(); // no marketing

form.flatten();

 

const pdfBytes = await pdfDoc.save();

res.setHeader('Content-Type', 'application/pdf');

res.setHeader('Content-Disposition', `attachment; filename="${filename}"`);

res.send(Buffer.from(pdfBytes));

 

 

Acceptance criteria

•       All 4 endpoints return correct data for a valid token and owned resource.

•       All 4 endpoints return 401 for missing/invalid token.

•       Routes 2, 3, 4 return 403 when owner does not own the resource.

•       PDF download opens in a viewer, all filled fields are correct, form is flattened (not editable).

•       No PII appears in any HTTP response except Routes 3 and 4, which require auth.

AGENT 4

Frontend · TypeScript contracts · Authenticated fetch functions

 

 

Goal

All API communication is typed end-to-end. No any types. No raw fetch calls outside endpoints.ts. The dashboard and all future components import from this layer only — never call fetch directly.

  id:         string;

2. endpoints.ts — authenticated fetch functions

const BASE = import.meta.env.VITE_API_BASE_URL ?? '';

 

function authHeaders(token: string) {

  return { Authorization: `Bearer ${token}`,

           'Content-Type': 'application/json' };

}

 

export async function fetchProperties(token: string): Promise<Property[]> {

  const res = await fetch(`${BASE}/v1/owner/properties`,

    { headers: authHeaders(token) });

  if (!res.ok) throw new ApiError(res.status, await res.text());

  return res.json();

}

 

export async function fetchSubmissions(propertyId: string, token: string)

    : Promise<SubmissionSummary[]> {

  const res = await fetch(

    `${BASE}/v1/owner/properties/${propertyId}/submissions`,

    { headers: authHeaders(token) });

  if (!res.ok) throw new ApiError(res.status, await res.text());

  return res.json();

}

 

export async function fetchSubmissionDetail(id: string, token: string)

    : Promise<SubmissionDetail> {

  const res = await fetch(`${BASE}/v1/owner/submissions/${id}`,

    { headers: authHeaders(token) });

  if (!res.ok) throw new ApiError(res.status, await res.text());

  return res.json();

}

 

export async function downloadSubmissionPdf(id: string, token: string)

    : Promise<Blob> {

  const res = await fetch(`${BASE}/v1/owner/submissions/${id}/pdf`,

    { headers: authHeaders(token) });

  if (!res.ok) throw new ApiError(res.status, await res.text());

  return res.blob();

}

 

export class ApiError extends Error {

  constructor(public status: number, message: string) {

    super(message); this.name = 'ApiError';

  }

}

 

 

3. Auth token source

The token comes from the existing login flow. Retrieve it as follows (adjust to match your actual auth implementation):

 

•       If using a React context: const { token } = useAuth()

•       If using localStorage (existing pattern): localStorage.getItem('ownerToken')

•       If using a session cookie: the fetch calls need credentials: 'include' and no Authorization header — confirm with Agent 1 which pattern is in use.

Important

Do not hardcode a token. Do not store the token in a React state variable that is initialised from a hardcoded string. The token source must be the actual login flow output.

 

 

Acceptance criteria

•       TypeScript compiles with no errors across all 4 fetch functions.

•       fetchProperties returns Property[] from the MSW mock.

•       fetchSubmissionDetail returns a fully typed SubmissionDetail including payload.

•       downloadSubmissionPdf returns a Blob and the filename is extractable from Content-Disposition.

•       ApiError is thrown (not swallowed) on 401, 403, 404 responses.

AGENT 8

Print / Download Form

Frontend · PDF blob download · No client-side PDF generation

 

 

Critical constraint

No pdf-lib. No PDF generation in the frontend. The Print / Download Form button calls GET /v1/owner/submissions/:id/pdf, receives a Blob from the server, and triggers a browser download. The server (Agent 2) has already filled and flattened the PDF. The frontend only downloads it.

 

 

Button behaviour — step by step

5.     User clicks 'Print / Download Form'.

6.     Button enters disabled state, label changes to '⏳ Generating…'.

7.     Call downloadSubmissionPdf(selectedSubmissionId, token) from endpoints.ts.

8.     On success: receive Blob with Content-Type application/pdf.

9.     Extract filename from Content-Disposition response header (see below).

10.   Create object URL: URL.createObjectURL(blob).

11.   Create a temporary <a> element: href = objectURL, download = filename.

12.   Programmatically click the <a> element.

13.   Revoke the object URL: URL.revokeObjectURL(objectURL).

14.   Button label changes to '✓ Downloaded' for 2500ms, then resets to '🖨 Print / Download Form'.

 

 

Filename extraction

The server sets Content-Disposition: attachment; filename="Matkustajailmoitus_Torres_AnaMaria.pdf". Extract it as follows:

 

// In downloadSubmissionPdf or at the call site:

const disposition = res.headers.get('Content-Disposition') ?? '';

const match = disposition.match(/filename="([^"]+)"/);

const filename = match?.[1] ?? 'Matkustajailmoitus.pdf';

 

Because downloadSubmissionPdf in endpoints.ts returns only the Blob, the response headers are not accessible after the fact. Two options:

•       Option A (preferred): Return { blob: Blob, filename: string } from downloadSubmissionPdf instead of just Blob.

•       Option B: Handle the raw response in the component and extract headers before calling .blob().

Implement Option A — update the function signature in endpoints.ts accordingly and update contracts.ts if needed.

 

 

Error handling

•       401: Redirect to login (or call the existing auth logout handler).

•       403: Show inline error: 'You do not have access to this submission.'

•       404: Show inline error: 'Submission not found.'

•       Network error: Show inline error: 'Download failed — please try again.'

•       All errors reset the button to its default state after display.
